

## 협업 가이드

2026-10-29부터 `main` + 작업별 브랜치 + PR 리뷰 + Squash merge를 적용한다. 모든 PR의 병합 대상은 `main`이며 `develop`은 운영하지 않는다. 아래 GitHub 설정 항목은 적용해야 할 운영 기준으로, 실제 설정 여부는 저장소 관리자가 별도로 확인한다.

> **팀원 필독:** PR을 만들었다는 것만으로 병합 조건을 충족하지 않습니다. 작성자 외 팀원 1명의 **GitHub `Approve`**, 변경에 맞는 검증, 미해결 수정 요청·리뷰 대화·충돌 해소를 확인한 뒤 **Squash and merge**해 주세요. 수정 완료 댓글·메신저 확인·AI 검토 결과는 팀원의 GitHub 승인을 대신하지 않습니다. 보호 설정이 적용되기 전에도 이 절차를 지켜 주세요.

### 1. 브랜치 전략

| 브랜치 | 용도 | 예시 |
| --- | --- | --- |
| `main` | 앱 실행과 핵심 기능 확인이 가능한 통합본 | 직접 푸시하지 않고 PR로 반영 |
| `feature/<작업명>` | 기능 추가 | `feature/regional-welfare` |
| `fix/<문제명>` | 오류 수정 | `fix/recipe-step-order` |
| `refactor/<대상>` | 동작을 유지하는 구조 개선 | `refactor/recipe-repository` |
| `docs/<문서명>` | 문서 추가·수정 | `docs/api-contract` |
| `chore/<작업명>` | 개발 환경·빌드·CI 설정 | `chore/flutter-ci` |

- 사람별 브랜치 대신 작업별 브랜치를 사용한다. 이름은 영문 소문자와 하이픈으로 작성한다.
- Codex가 만드는 브랜치는 `codex/<유형>-<작업명>`을 사용한다. 예: `codex/docs-collaboration-rules`. 리뷰·병합 규칙은 동일하다.
- 통합·충돌 해결 작업도 위 명명 규칙을 사용한다. 예: `fix/nutrition-integration`, `codex/fix-nutrition-integration`. 예외가 필요하면 작업 목적과 이유를 PR에 기록하고 팀과 합의한다.
- 최신 `main`에서 분기하고, 하나의 독립적인 변경을 마치면 PR을 만든다. 큰 Asana 작업은 API 계약·서버 구현·앱 연동처럼 여러 PR로 나눌 수 있다.
- fork에서 작업할 때도 PR 대상은 팀 저장소의 `main`이다. `origin`이 개인 fork라면 팀 저장소 원격인 `upstream/main`을 기준으로 최신 변경을 확인한다.
- 병합한 브랜치는 삭제한다. Squash merge 후 같은 브랜치에서 다음 작업을 이어가지 않는다.
- fork의 작업 브랜치는 소유자가 정리한다. 검토 중이거나 미병합 변경이 남은 브랜치는 삭제하지 않는다.
- 시연·제출 전 검증한 커밋에는 `demo-2026-11-06` 같은 태그를 남기고 APK·검증 기록과 연결한다. 태그는 실제 검증 후 생성한다.

### 2. 커밋 메시지

형식은 `타입(범위): 변경 내용`이다. 범위는 선택 사항이며, 타입·범위는 영어 소문자, 설명은 한국어를 기본으로 한다. 범위 예시는 `app`, `api`, `data`, `ai`, `admin`, `plan`이다.

| 타입 | 사용 기준 |
| --- | --- |
| `feat` | 새로운 기능 |
| `fix` | 잘못된 동작 수정 |
| `refactor` | 외부 동작을 유지하는 코드 구조 개선 |
| `docs` | 문서 |
| `test` | 테스트 추가·수정 |
| `style` | 포맷·공백 등 동작에 영향 없는 코드 표기 변경 |
| `perf` | 성능 개선 |
| `build` | 빌드·의존성 변경 |
| `ci` | 자동 검증·배포 설정 |
| `chore` | 나머지 관리 작업 |
| `revert` | 기존 변경 되돌리기 |

```text
feat(app): 사용자 건강 상태 입력 화면 추가
feat(api): 건강 상태별 식단 추천 API 추가
fix(app): 레시피 조리 단계가 누락되는 문제 수정
refactor(data): 복지 데이터 정규화 로직 분리
docs(plan): 기업 방문 피드백과 구현 일정 반영
test(api): 알레르기 제외 조건 검증 추가
ci: Flutter 정적 분석과 테스트 자동 실행
```

- 한 커밋에는 하나의 목적을 담는다. `수정`, `최종`, `진짜최종`처럼 내용을 알 수 없는 메시지는 사용하지 않는다.
- `style`은 화면 디자인 변경을 뜻하지 않는다. 새 화면은 `feat`, 잘리는 글자 수정은 `fix`처럼 변경 목적에 맞춘다.
- 복잡한 변경은 제목 다음에 빈 줄을 두고 변경 이유·영향을 본문에 적는다.
- 기존 API와 호환되지 않는 변경은 사전 합의하고 `feat(api)!: ...`처럼 `!`와 본문의 `BREAKING CHANGE:`로 영향·전환 방법을 설명한다.
- API 키·비밀번호·개인 사용자 자료·`.env`·생성된 빌드 결과는 커밋하지 않는다. 과거 이력을 규칙에 맞추려고 다시 작성하지 않는다.

### 3. PR 작성과 리뷰

PR 하나는 독립적으로 검토·검증·되돌릴 수 있는 변경 하나를 기준으로 한다. PR 제목은 커밋 메시지 형식을 따른다. 작업 중에는 Draft PR로 공유할 수 있다.

새 PR은 [기본 PR 템플릿](.github/pull_request_template.md)을 사용한다. 템플릿이 아직 기본 브랜치에 반영되지 않았거나 본문이 자동 입력되지 않으면 아래 양식과 템플릿의 체크리스트를 복사한다. 체크 표시는 검증·승인 기록 자체를 대신하지 않는다.

```markdown
## 변경 목적과 내용
- 해결할 문제와 변경 후 동작

## 확인 결과
- 실제 실행한 검증 명령과 결과
- 화면 변경이면 스크린샷 또는 짧은 영상
- 실행하지 못한 검증이 있으면 이유

## 영향과 주의사항
- API·DB·환경변수 변경과 전환 절차
- 알려진 제한 사항

## 관련 작업
- Asana 작업 링크
```

- 작성자 외 팀원 1명 이상의 승인이 필요하다. 미해결 수정 요청·리뷰 대화·충돌이 있으면 병합하지 않는다.
- 리뷰어는 GitHub의 **Review changes → Approve / Request changes**로 판단을 남긴다. 일반 댓글만으로 승인·수정 요청 상태가 자동 변경되지는 않는다.
- API 요청·응답이 바뀌면 앱·백엔드 담당자가 함께 확인한다. 데이터·RAG·관리자 변경도 해당 소비자와 필드·단위·오류 동작을 맞춘다.
- 작성자는 검증 근거를 기록하고, 승인 후 작성자 또는 저장소 관리자가 병합한다. 중요한 후속 수정이 있으면 다시 리뷰를 요청한다.
- `Request changes`를 받은 PR은 수정 커밋과 재검증 결과를 올리고 리뷰어에게 재검토를 요청한다. 리뷰어가 수정 반영을 확인하고 `Approve`한 뒤 병합한다. 수정 전 커밋의 승인만으로 중요한 후속 수정을 병합하지 않는다.
- Flutter 변경은 `src/frontend`에서 `flutter analyze`, `flutter test`를 실행한다. 화면·기기 기능 변경은 에뮬레이터에서 해당 흐름도 확인한다.
- Python·관리자 웹은 구현된 구성에 맞는 테스트·정적 검사·실행 확인을 수행한다. 없는 테스트나 서버가 통과했다고 기록하지 않는다.
- 문서만 변경했다면 내용·상대 링크·`git diff --check`를 확인한다. 변경과 무관한 전체 앱 빌드는 요구하지 않는다.

리뷰 요청 기준은 다음과 같다. 모두 작성자 외 리뷰이며, 해당자가 작성자이면 다른 협업자가 리뷰한다. 표는 리뷰 요청의 기본 기준이고, 승인 인원 최소 기준은 1명이다.

| 변경 영역 | 기본 리뷰 요청 대상 |
| --- | --- |
| Flutter 앱·접근성 | 이진녕, 데이터 표시가 바뀌면 최재영과 필드 확인 |
| 백엔드 API·사용자·추천·DB | 김찬형, 원천 필드·적재가 바뀌면 최재영과 확인 |
| 수집·전처리·식품 매핑·RAG 인덱스 | 이진녕, 품질 근거는 김민찬과 확인 |
| 관리자 웹·평가 | 이진녕, 데이터 검수는 최재영과 확인 |
| 기획·일정·문서 | 조의현 또는 김민찬, 기술 내용은 해당 구현 담당자와 확인 |

### 4. 병합·충돌·복구

- 작업 브랜치 → `main`은 **Squash and merge**로 통일한다. 최종 커밋 제목은 PR 제목을 기준으로 정리한다.
- 병합 조건: 팀원 1명 이상 승인, 수정 요청·충돌 해결, 변경에 맞는 검증 통과, 필요한 API·설정 문서 반영.
- 작업 중 최신 변경을 받을 때는 먼저 작업을 커밋하고 `git fetch origin`, `git merge origin/main` 순서로 작업 브랜치에 반영한다.
- 충돌은 해당 코드 담당자와 변경 의도를 확인해 해결하고 관련 검증을 다시 수행한다. 다른 사람의 변경을 통째로 덮어쓰지 않는다.
- 공유 브랜치의 이력을 다시 쓰거나 강제 푸시하지 않는다. `main` 병합 후 문제가 있으면 `revert` 커밋을 담은 PR로 되돌린다.
- 긴급 수정도 최신 `main`에서 `fix/<문제명>`을 만들고 리뷰·검증·PR 절차를 따른다.

병합 담당자는 다음을 최종 확인한다.

- [ ] 대상이 팀 저장소의 `main`이고 이번 작업 외 변경이 섞이지 않았다.
- [ ] 작성자 외 팀원의 유효한 `Approve`가 있으며 중요한 후속 변경도 재검토됐다.
- [ ] 수정 요청·미해결 리뷰 대화·충돌이 없고 실행한 검증 결과가 PR에 기록돼 있다.
- [ ] PR과 Asana에 작업 브랜치·관련 PR·남은 범위를 서로 연결했다.
- [ ] **Squash and merge**를 선택하고 최종 제목을 PR 제목 기준으로 확인했다.
- [ ] 병합 후 `main` 동작과 전체 완료 기준을 확인하고 작업 기록·브랜치를 정리한다.

다른 PR로 대체해 통합하는 경우 원본·대체 PR에 서로의 링크와 대체 이유를 남기고 Asana에도 두 PR을 기록한다. 대체 PR도 승인·검증 절차를 새로 거친다.

### 5. GitHub 설정 기준

저장소 관리자가 다음 설정을 확인한다. 문서에 적힌 기준 자체가 설정 적용을 의미하지 않는다.

- `main`의 PR 필수, 작성자 외 승인 1명, 리뷰 대화 해결을 요구한다.
- 강제 푸시와 `main` 삭제를 금지하고 병합 후 작업 브랜치를 자동 삭제한다.
- PR 병합 방식은 Squash merge를 사용한다. Squash 커밋의 기본 제목은 PR 제목으로 설정한다.
- 자동 검증을 구축하고 실제 동작을 확인한 뒤 해당 검사 이름을 병합 필수 조건으로 등록한다. 현재 저장소에는 GitHub Actions 워크플로가 없다.

**관리자 후속 조치:** 2026-11-06 조회에서 `main`은 `protected=false`, 저장소 ruleset 목록은 비어 있었고 merge commit·rebase 허용 및 병합 후 자동 삭제 비활성 상태를 확인했다. 보호 설정 상세 API는 연결 도구의 권한 제한으로 조회하지 못했고 브라우저 설정 변경도 완료하지 못했다. 아래 항목은 설정 적용 완료가 아니라 관리자가 처리하고 재확인할 목록이다.

| 위치 | 적용하고 확인할 설정 |
| --- | --- |
| Settings → Rules → Rulesets 또는 Branches | `main` 대상 PR 필수·승인 최소 1명·리뷰 대화 해결, 관리자/우회 권한의 적용 범위 확인 |
| 같은 보호 규칙 | 후속 변경 시 오래된 승인 무효화, 강제 푸시·브랜치 삭제 금지 |
| Settings → General → Pull Requests | Squash만 허용하고 merge commit·rebase 병합 비활성화 |
| 같은 Pull Requests 설정 | Squash 기본 제목을 PR 제목으로 설정하고 병합 후 브랜치 자동 삭제 활성화 |
| CI 구축·실행 확인 이후 | 실제 성공한 검사 이름을 필수 상태 검사로 등록. 존재하지 않는 검사 이름을 먼저 요구하지 않음 |

설정을 바꾼 관리자는 확인 날짜·적용 대상을 작업 기록에 남기고 위 조회 상태를 갱신한다. 이미 병합된 이력을 재작성하거나 과거 PR에 소급 승인을 남겨 준수한 것처럼 만들지 않는다.

### 6. Asana와 연결하는 작업 순서

1. 본인 작업의 범위·선행 조건·완료 기준·시작일·마감일을 확인한다. 추가 기능의 보류는 별도 합의 전까지 유지한다.
2. 최신 `main`에서 작업별 브랜치를 만들고 Asana 작업 설명에 브랜치 이름을 기록한다.
3. PR을 열어 PR 본문에 Asana 링크를, Asana 작업에는 PR 링크를 기록한다. 여러 PR이면 모두 연결한다.
4. 리뷰 요청·수정·검증 결과를 남기고 승인 후 Squash merge한다.
5. `main`에 반영된 변경의 동작과 해당 작업의 전체 완료 기준을 확인한 후 Asana를 완료 처리한다. 일부 PR 병합만으로 전체 작업을 완료 처리하지 않는다.

작업 설명에는 다음 기록란을 사용한다. Asana 링크만으로 GitHub 병합·완료 상태가 자동 동기화되지는 않으며 담당자가 갱신한다.

```text
작업 브랜치: 착수 시 기록
관련 PR: 생성 시 기록(복수 가능)
리뷰 요청: 작성자 외 해당 협업자
검증 결과: 실행 명령·결과 또는 문서 확인 내용
병합 커밋: 병합 후 기록
완료 확인: main 반영·동작·전체 완료 기준 확인 후 기록
```

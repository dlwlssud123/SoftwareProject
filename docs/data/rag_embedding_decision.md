## 1. 결정

| 항목 | 결정 |
|---|---|
| 모델 | [`nlpai-lab/KURE-v1`](https://huggingface.co/nlpai-lab/KURE-v1) (고려대 NLP&AI 연구실, BAAI/bge-m3를 한국어 자료로 추가 학습). revision `8b418a58414668e75532ed045c22d9ca018ae2b2` (2026-09-07) |
| 라이선스 | MIT (모델 카드 확인, 2026-11-07) |
| 벡터 | **1024차원**, CLS pooling, 길이 1로 정규화. 질문·문서에 붙이는 접두어 없음. 최대 입력 8,192 토큰 |
| 경량화 | **하지 않음.** 원본 fp32 가중치를 그대로 쓴다(품질 우선) |
| 실행 서버 | 기업 서버에서 먼저 → 시연에 문제가 될 만큼 느리거나 메모리가 모자라면 최재영 서버(ARM)로 옮김 |
| 저장 | PostgreSQL + pgvector(기획서 확정), `vector(1024)` 한 칸 |
| 비용 | 임베딩 API 호출 비용 없음. 서버 고정비만 든다 → 12장 운영비의 '임베딩' 항목 |

RAG는 빼지 않는다. 자료 없이 대화 AI만 쓰면 지역 복지 사업명·문의처를 지어낼 수 있다(CORE-05 "공식 경로 안내").

## 2. 왜 KURE-v1인가

모델 카드의 한국어 검색 평가 8종 평균(Ko-StrategyQA, AutoRAGRetrieval, PublicHealthQA, MIRACL 등):

| 모델 | 차원 | Recall@1 | Recall@3 | Recall@5 | 비고 |
|---|---:|---:|---:|---:|---|
| **nlpai-lab/KURE-v1** | 1024 | **0.526** | **0.687** | **0.739** | MIT |
| BAAI/bge-m3 | 1024 | 0.518 | 0.675 | 0.730 | MIT, KURE의 바탕 모델 |
| intfloat/multilingual-e5-large | 1024 | 0.501 | 0.658 | 0.701 | 질문·문서 접두어 필요 |

- 설치형 후보 중 한국어 검색 수치가 가장 높고, 외부 API에 어르신 질문을 보내지 않는다.
- 차이는 크지 않으므로 우리 자료로 다시 확인한다. 복지·레시피 질문을 어르신 말투로 바꿔 쓴 평가 질문으로 Hit@k를 재고 결과를 보고서로 남긴다(RAG 인덱스 작업).
- 모델을 바꾸더라도 청크 약 3천 건을 다시 임베딩하면 되고, 표는 `embedding` 칸 차원만 바뀐다.

## 3. 서버에서 돌리는 방식

| 구분 | 언제 | 어디서 |
|---|---|---|
| 문서 임베딩 | 처음 한 번 전체(약 3천 청크), 그다음은 갱신 때 **바뀐 청크만**(`content_sha256` 비교) | 갱신 worker. 처음 전체 임베딩은 서버가 아니어도 됨 |
| 질문 임베딩 | AI 도우미 요청마다 1회(짧은 문장) | AI 도우미 API 서버 |

- **같은 모델·revision이면 어느 컴퓨터에서 만든 벡터든 그대로 쓸 수 있다.** 서버를 옮겨도 다시 임베딩하지 않는다. 그래서 `embedding_model` 칸에 revision까지 적고, 값이 다른 벡터는 섞지 않는다.
- **메모리:** 가중치 2.27GB(fp32)에 실행 메모리가 더해져 약 3GB를 예상한다(실측으로 갱신). 모델은 **한 프로세스에만** 올린다. FastAPI 워커를 여러 개 띄우면 워커마다 모델이 올라가 메모리가 그만큼 늘어난다.
- **기업 서버 조건(11/06 확인):** i7-7700(4코어 8스레드), 메모리 15GB 중 여유 약 5.9GB, 스왑 2GB 사용 중, Ubuntu 22.04, Python 3.10, Docker 있음.
  - 우리 코드는 Python 3.12 기준이라 Docker `python:3.12` 이미지에서 돌린다.
  - GPU(GTX 660)는 최신 PyTorch가 지원하지 않아 CPU로 돌린다. torch는 **CPU 전용 판**으로 설치한다. 리눅스 기본 torch는 쓰지 못하는 CUDA 라이브러리를 수 GB 같이 받는다.
- **최재영 서버(ARM) 조건:** Neoverse-N1 4코어, 메모리 23GB 중 여유 약 21GB, Ubuntu 24.04, Python 3.12, Docker 없음. ARM용 CPU torch로 돌린다.
- **옮기는 기준(제안):** 기업 서버에서 모델을 올린 상태로 ① 질문 임베딩 p95가 0.5초를 넘거나 ② 남은 메모리가 1GB 아래로 떨어지거나 스왑이 계속 늘면 ARM 서버로 옮긴다. 측정 명령은 RAG 인덱스 작업에서 제공한다.

## 4. 청크 규칙

| 원천 | 청크 | 머리말·내용 |
|---|---|---|
| 복지(중앙·지자체) 1,468건 | 사업 1건 = 1청크(`section='all'`). 1,000자를 넘으면 항목 경계(개요·지원 내용·신청)로 나눔 | 모든 청크 앞에 `[복지] 사업명 (지역)` 머리말. 요약·지원 대상·선정 기준·지원 내용·신청 방법·문의처를 **원문 그대로** |
| 레시피 1,156건 | 레시피 1건 = 1청크. 길면 만드는 법을 따로 나눔 | 이름·분류·조리법·재료(분량 원문)·만드는 법·저염 팁·영양 원문 값 |

- 복지 본문(사업명~신청 방법 설명) 길이는 중앙값 307자, 상위 10% 693자, 최대 3,006자라 대부분 나누지 않는다.
- 수급 자격을 판정하는 문장은 만들지 않는다. 대상·기준은 원문 그대로 둔다(`welfare_contract.md` 1절).
- 레시피 `hold` 7건(조리 단계 누락 등)은 청크를 만들지 않는다. `flagged`는 넣고 `quality_status`·`quality_flags`로 표시한다(`recipe_contract.md` 규칙 3).
- 레시피 알레르기는 본문에 넣지 않고 `allergens` 칸에 둔다. 검색 **전에** 사용자 알레르기로 거른다. 재료명으로 추정한 값이라 확인 필요(needs_check) 종류도 함께 넣는다.
- `chunk_id = <source_type>:<source_id>:<section>:<번호>`라서 다시 만들어도 값이 같다. 원천에서 사라진 사업은 `status='retracted'`로 바꾼다.

## 5. 검색 순서 (AI 도우미 API)

1. 앱 프로필의 시도·시군구를 `welfare.query.resolve_region()`으로 정규화한다(광주·전남 통합, `남구`처럼 이름이 같은 시군구는 시도와 쌍으로 맞춤).
2. 질문을 KURE-v1로 임베딩한다.
3. SQL 조건으로 먼저 거른다: `status='active'`, 원천 종류, 지역(전국 + 내 시도 전체 + 내 시군구), 끝난 사업 제외, 레시피는 알레르기 제외.
4. 코사인 거리 순으로 상위 k개(기본 5개)를 가져온다. SQL 예는 `sql/rag_chunk_draft.sql` 아래쪽에 있다.
5. 가장 높은 유사도가 문턱값보다 낮으면 "근거 없음"으로 보고, 대화 AI가 지어내지 않고 공식 문의처를 안내하게 한다. 문턱값은 평가 질문(답이 없는 질문 포함)으로 정해 보고서에 적는다.

- 벡터 색인(HNSW)은 지금 만들지 않는다. 약 3천 건은 전부 비교해도 수 ms이고, 지역 조건과 충돌하지 않는다(정확 검색). 수만 건을 넘으면 추가한다.
- 시범 지역은 **대구광역시 남구**(11/07 팀 결정, 잠정). 화면·검색은 남구 사업 → 대구시 전체 사업 → 전국 사업 순으로 함께 보여 준다(현재 남구 4건 / 대구시 전체 10건 / 전국 130건).

## 7. 확인할 것 (이진녕)

1. 복지·레시피 원본 표 이름과 키. `rag_chunk.source_id`에 외래 키를 걸지, 원천 종류별로 따로 연결할지
2. 판본 전환 방식. 청크도 판본별로 보관할지(기본 키에 `data_version` 포함), 최신만 두고 `status`로 관리할지
3. 질문 임베딩 위치. FastAPI 프로세스 안에서 할지, 모델 하나만 올린 작은 임베딩 서비스로 뺄지(워커가 여러 개면 후자)
4. 기관 자체 안내(복지관 프로그램 등)를 검색에 넣는 것은 BM 후속 정리(기관 제공 기능 범위) 이후. 지금은 `source_type` 값만 늘리면 되게 둔다

## 1. 결정

| 항목 | 결정 |
|---|---|
| 모델 | [`nlpai-lab/KURE-v1`](https://huggingface.co/nlpai-lab/KURE-v1) (고려대 NLP&AI 연구실, BAAI/bge-m3를 한국어 자료로 추가 학습). revision `8b418a58414668e75532ed045c22d9ca018ae2b2` (2026-09-07) |
| 라이선스 | MIT (모델 카드 확인, 2026-11-07) |
| 벡터 | **1024차원**, CLS pooling, 길이 1로 정규화. 질문·문서에 붙이는 접두어 없음. 최대 입력 8,192 토큰 |
| 경량화 | **하지 않음.** 원본 fp32 가중치를 그대로 쓴다(품질 우선) |
| 실행 서버 | 기업 서버에서 먼저 → 시연에 문제가 될 만큼 느리거나 메모리가 모자라면 최재영 서버(ARM)로 옮김 |
| 저장 | PostgreSQL + pgvector(기획서 확정), `vector(1024)` 한 칸 |
| 비용 | 임베딩 API 호출 비용 없음. 서버 고정비만 든다 → 12장 운영비의 '임베딩' 항목 |

RAG는 빼지 않는다. 자료 없이 대화 AI만 쓰면 지역 복지 사업명·문의처를 지어낼 수 있다(CORE-05 "공식 경로 안내").

## 2. 왜 KURE-v1인가

모델 카드의 한국어 검색 평가 8종 평균(Ko-StrategyQA, AutoRAGRetrieval, PublicHealthQA, MIRACL 등):

| 모델 | 차원 | Recall@1 | Recall@3 | Recall@5 | 비고 |
|---|---:|---:|---:|---:|---|
| **nlpai-lab/KURE-v1** | 1024 | **0.526** | **0.687** | **0.739** | MIT |
| BAAI/bge-m3 | 1024 | 0.518 | 0.675 | 0.730 | MIT, KURE의 바탕 모델 |
| intfloat/multilingual-e5-large | 1024 | 0.501 | 0.658 | 0.701 | 질문·문서 접두어 필요 |

- 설치형 후보 중 한국어 검색 수치가 가장 높고, 외부 API에 어르신 질문을 보내지 않는다.
- 차이는 크지 않으므로 우리 자료로 다시 확인한다. 복지·레시피 질문을 어르신 말투로 바꿔 쓴 평가 질문으로 Hit@k를 재고 결과를 보고서로 남긴다(RAG 인덱스 작업).
- 모델을 바꾸더라도 청크 약 3천 건을 다시 임베딩하면 되고, 표는 `embedding` 칸 차원만 바뀐다.

## 3. 서버에서 돌리는 방식

| 구분 | 언제 | 어디서 |
|---|---|---|
| 문서 임베딩 | 처음 한 번 전체(약 3천 청크), 그다음은 갱신 때 **바뀐 청크만**(`content_sha256` 비교) | 갱신 worker. 처음 전체 임베딩은 서버가 아니어도 됨 |
| 질문 임베딩 | AI 도우미 요청마다 1회(짧은 문장) | AI 도우미 API 서버 |

- **같은 모델·revision이면 어느 컴퓨터에서 만든 벡터든 그대로 쓸 수 있다.** 서버를 옮겨도 다시 임베딩하지 않는다. 그래서 `embedding_model` 칸에 revision까지 적고, 값이 다른 벡터는 섞지 않는다.
- **메모리:** 가중치 2.27GB(fp32)에 실행 메모리가 더해져 약 3GB를 예상한다(실측으로 갱신). 모델은 **한 프로세스에만** 올린다. FastAPI 워커를 여러 개 띄우면 워커마다 모델이 올라가 메모리가 그만큼 늘어난다.
- **기업 서버 조건(11/06 확인):** i7-7700(4코어 8스레드), 메모리 15GB 중 여유 약 5.9GB, 스왑 2GB 사용 중, Ubuntu 22.04, Python 3.10, Docker 있음.
  - 우리 코드는 Python 3.12 기준이라 Docker `python:3.12` 이미지에서 돌린다.
  - GPU(GTX 660)는 최신 PyTorch가 지원하지 않아 CPU로 돌린다. torch는 **CPU 전용 판**으로 설치한다. 리눅스 기본 torch는 쓰지 못하는 CUDA 라이브러리를 수 GB 같이 받는다.
- **최재영 서버(ARM) 조건:** Neoverse-N1 4코어, 메모리 23GB 중 여유 약 21GB, Ubuntu 24.04, Python 3.12, Docker 없음. ARM용 CPU torch로 돌린다.
- **옮기는 기준(제안):** 기업 서버에서 모델을 올린 상태로 ① 질문 임베딩 p95가 0.5초를 넘거나 ② 남은 메모리가 1GB 아래로 떨어지거나 스왑이 계속 늘면 ARM 서버로 옮긴다. 측정 명령은 RAG 인덱스 작업에서 제공한다.

| 원천 | 청크 | 머리말·내용 |
|---|---|---|
| 복지(중앙·지자체) 1,468건 | 사업 1건 = 1청크(`section='all'`). 1,000자를 넘으면 항목 경계(개요·지원 내용·신청)로 나눔 | 모든 청크 앞에 `[복지] 사업명 (지역)` 머리말. 요약·지원 대상·선정 기준·지원 내용·신청 방법·문의처를 **원문 그대로** |
| 레시피 1,156건 | 레시피 1건 = 1청크. 길면 만드는 법을 따로 나눔 | 이름·분류·조리법·재료(분량 원문)·만드는 법·저염 팁·영양 원문 값 |

- 복지 본문(사업명~신청 방법 설명) 길이는 중앙값 307자, 상위 10% 693자, 최대 3,006자라 대부분 나누지 않는다.
- 수급 자격을 판정하는 문장은 만들지 않는다. 대상·기준은 원문 그대로 둔다(`welfare_contract.md` 1절).
- 레시피 `hold` 7건(조리 단계 누락 등)은 청크를 만들지 않는다. `flagged`는 넣고 `quality_status`·`quality_flags`로 표시한다(`recipe_contract.md` 규칙 3).
- 레시피 알레르기는 본문에 넣지 않고 `allergens` 칸에 둔다. 검색 **전에** 사용자 알레르기로 거른다. 재료명으로 추정한 값이라 확인 필요(needs_check) 종류도 함께 넣는다.
- `chunk_id = <source_type>:<source_id>:<section>:<번호>`라서 다시 만들어도 값이 같다. 원천에서 사라진 사업은 다음 인덱스 판본에 없으므로 판본 전환과 함께 검색에서 빠진다(9절). 다음 판본을 기다리지 않고 바로 숨길 때만 `status='retracted'`.

## 5. 검색 순서 (AI 도우미 API)

1. 앱 프로필의 시도·시군구를 `welfare.query.resolve_region()`으로 정규화한다(광주·전남 통합, `남구`처럼 이름이 같은 시군구는 시도와 쌍으로 맞춤).
2. 질문을 KURE-v1로 임베딩한다.
3. SQL 조건으로 먼저 거른다: **활성 인덱스 판본**(`rag_index_version.status='active'`), **질문과 같은 임베딩 모델**(`embedding_model = :embedding_model`), **원본 표에 지금 게시 중인 그 내용**(`rag_source_active` 레코드 해시 일치), `status='active'`, 원천 종류, 지역(전국 + 내 시도 전체 + 내 시군구), 끝난 사업 제외, 레시피는 알레르기 제외.
4. 코사인 거리 순으로 상위 k개(기본 5개)를 가져온다. SQL 예는 `sql/rag_chunk_draft.sql` 아래쪽에 있다.
5. 가장 높은 유사도가 0.40보다 낮으면 "근거 없음"으로 보고, 대화 AI가 지어내지 않고 공식 문의처를 안내하게 한다. 0.40 이상이어도 근거가 질문과 맞지 않을 수 있어 프롬프트에 "근거가 질문과 맞지 않으면 모른다고 하고 문의처를 안내, 근거에 없는 사업·금액·전화번호를 만들지 않기"를 넣는다(8절 평가 결과: 유사도만으로는 완전히 가르지 못함).

- 벡터 색인(HNSW)은 지금 만들지 않는다. 약 3천 건은 전부 비교해도 수 ms이고, 지역 조건과 충돌하지 않는다(정확 검색). 수만 건을 넘으면 추가한다.
- 시범 지역은 **대구광역시 남구**(11/07 팀 결정, 잠정). 화면·검색은 남구 사업 → 대구시 전체 사업 → 전국 사업 순으로 함께 보여 준다(현재 남구 4건 / 대구시 전체 10건 / 전국 130건).

## 9. 11/07 리뷰 반영 (SQL 초안 v2)

PR #11 리뷰(이진녕) 세 가지를 반영했다.

| 리뷰 | 반영 |
|---|---|
| [P2] 모델·revision 필터 누락 — 다른 모델 벡터가 1위로 나옴 | 검색 예 1·2에 `c.embedding_model = :embedding_model`. 실데이터 재현: 다른 모델 행 하나를 섞자 조건 없이는 그 행이 유사도 1.0으로 1위, 조건을 넣으면 정상 결과(경로우대사업 0.458). 파이썬 검색도 인덱스 모델 ≠ 질문 모델이면 거부 |
| 판본 전환 — 부분 갱신 중 이전 청크가 검색됨 | 인덱스 판본 표 `rag_index_version`(loading/active/retired/failed, 활성은 하나만) + `rag_chunk` 기본 키 (`index_version`, `chunk_id`). 판본을 통째로 `loading`으로 넣고, 행 수·모델이 manifest와 같으면 한 트랜잭션에서 활성만 바꿈. 검색은 활성 판본만 JOIN |
| (같은 지적) 원본 게시 상태 연결 | 청크에 원본 레코드 해시 `source_record_sha256`. 검색은 `rag_source_active`(원본 표의 지금 게시 레코드) JOIN으로 해시가 같은 청크만 씀 |
| 문서 수치 산출 근거 | 8절 표. manifest `sources`에서 보고서가 생성 |

- 실데이터 확인(pgvector 0.8.7, 2,880 청크): 적재 스크립트로 판본 활성 → 같은 판본 재실행은 건너뜀 → 새 판본 적재 중에는 이전 판본만 검색 → 전환 뒤 새 판본 → 되돌리기 → 건수 불일치 판본은 `failed`·종료 코드 3·이전 판본 유지 → 활성 두 개는 제약으로 거부 → 정리 뒤 활성 + 직전 판본만 남음 → 원본 표에서 사업을 내리거나 원본 해시가 바뀌면 RAG 판본이 그대로여도 그 사업이 바로 검색에서 빠지고, 원본을 되돌리면 다시 나옴. 평가 질문 38개는 v2 SQL 상위 5개가 파이썬 검색과 순서까지 같고 1회 약 9ms.
- 적재 스크립트(`load_index.sql`)는 `python -m agetech_data.rag.export`가 만든다(RAG 인덱스 작업 브랜치). 임베딩이 중간에 실패하면 manifest가 바뀌지 않아 새 판본 자체가 생기지 않는다.
- **원본 표 판본 전환과 RAG 판본 전환은 한 트랜잭션으로 묶지 않는다(11/07 결정).**
  - 이유: 복지는 하루 1회·레시피는 주 1회로 주기가 다르고, 묶으면 임베딩 실패가 복지 정보 갱신까지 막는다.
  - 대신 검색이 원본 표의 지금 게시 레코드와 레코드 해시를 대조한다. 원본이 먼저 바뀌어도 내려간 사업·바뀐 사업은 바로 빠지고(틀린 근거 대신 '없음'), 새 사업은 RAG 판본이 전환된 뒤부터 검색된다.
  - 순서: ① 원본 수집·정제 → ② 원본 표 적재·전환 → ③ `rag.index`(바뀐 청크만 임베딩) → ④ `load_index.sql`. RAG가 실패해도 ②는 그대로 진행된다.
  - 원본 표 쪽 할 일(이진녕): 실제 게시 DB 판본의 `fingerprint`를 `rag_source_active (source_type, source_id, record_sha256)`에 제공한다. 아래 11/09 보완 계약을 따른다.

## 10. 11/09 롤백 안전성과 게시 판본 대조 보완

SQL 초안 v3의 `rag_rollback_index(previous_version)`는 대상 존재·과거 활성화 이력·상태·청크 건수·모델 일치를 검증한 뒤 현재 활성 판본을 바꾼다. 없는 판본이나 `loading`·`failed` 판본, 활성화 이력이 없는 `retired`, 불완전한 청크는 오류로 거부하며 기존 활성 판본을 보존한다. 현재 활성 판본을 다시 지정하면 검증 후 같은 상태로 끝난다. 인덱스 표와 청크 표의 쓰기 잠금으로 적재·정리·동시 롤백을 직렬화하며 일반 검색 SELECT는 계속 허용한다.

`source_record_sha256`와 뷰의 `record_sha256`는 게시 판본 지문을 담는다. 레시피는 `recipe_revisions.fingerprint`, 중앙 복지는 `welfare_revisions.fingerprint`다. 원문 해시만 사용하면 같은 원문에 대한 보완·검증기·정규화 변경을 놓칠 수 있다. 게시 판본 지문은 이러한 변경을 포함한다. exporter는 해당 DB 판본의 지문을 읽어 청크에 복사해야 하며 기존 원문 해시 기반 청크는 다시 내보낸다. 실제 DB 테이블 이름을 사용한 뷰 예시는 SQL 초안에 있다.

이 파일의 11/07 실데이터 평가 수치는 당시 v2 기록이다. v3 롤백과 원문이 같은 판본 변경의 검색 제외는 PostgreSQL 격리 스키마의 자동 테스트로 확인한다. 임베딩 exporter·지자체 DB 적재·공고 게시 조건을 잇는 운영 뷰는 RAG 인덱스 작업에서 이 계약에 맞춰 연결한다.

# RAG 서버 측정 절차 — 기업 서버에 계속 둘지, ARM 서버로 옮길지

| 항목 | 내용 |
|---|---|
| 작성 | 최재영 (데이터) |
| 함께 할 사람 | 이진녕(백엔드 띄우기), 최재영(측정) |
| 결정 | 2026-11-07 "기업 서버에서 먼저, 시연에 문제가 될 만큼 느리면 최재영 서버(ARM)" — `rag_embedding_decision.md` 3절 |
| 도구 | `uv run python -m agetech_data.rag.bench` (옵션은 아래) |

임베딩 모델만 혼자 재면 **최소 조건**만 확인된다. 시연 때는 한 서버에 PostgreSQL·FastAPI·임베딩 모델이 같이 돌고 요청이 겹치므로, **백엔드와 같이 띄운 상태**에서 다시 재야 실제 판정이 된다.

## 0. 사전 점검 (서버에서, 1분)

```bash
free -h                         # 남은 메모리·스왑
top -b -o %MEM -n 1 | head -20  # 무엇이 메모리를 쓰는지
vmstat 1 5                      # si·so가 계속 0이면 스왑은 오래된 잔여, 숫자가 나오면 지금 메모리 압박
ollama ps                       # (Ollama가 있으면) 올라가 있는 모델·크기·유지 시간
nproc; df -h .; docker ps       # 코어 수, 디스크, 이미 떠 있는 컨테이너·포트
```

- 스왑이 이미 꽉 차 있으면 `bench`의 '스왑 증가' 기준은 늘어날 자리가 없어 항상 통과처럼 보인다. 이때 `bench`가 경고를 띄운다. 메모리가 모자라는 순간 느려지는 대신 **OOM으로 큰 프로세스가 강제 종료**될 수 있으므로 `vmstat`과 남은 메모리로 판단한다.
- `bench` 결과에도 측정 직전 메모리를 많이 쓰던 프로그램 이름별 합계가 찍힌다(`top_memory_before`, 리눅스만).

### 기업 서버 0단계 결과 (2026-11-07 17:39, 사용자 확인)

| 항목 | 값 |
|---|---|
| 메모리 | 15GB 중 사용 9.3GB, **바로 쓸 수 있는 양 5.9GB**(캐시 포함), 스왑 2GB **꽉 참**. 켜진 지 107일 |
| CPU·디스크 | 8스레드, 부하 0.2(98.5% 쉼), 디스크 여유 121GB |
| 메모리 많이 쓰는 것 | **ollama 약 6GB**(프로세스 3개, 로컬 LLM이 올라가 있음), java(gwcc 컨테이너) 0.7GB, 데스크톱(gnome-shell), claude·codex 세션, Next.js |
| Docker | `gwcc`(Tomcat, 8107), `gwcc-db`(MariaDB), `drone-db`(PostGIS 16, **5433**), `pdf-img-server`(9839) — 기업 다른 프로젝트와 같이 쓰는 서버 |

| `vmstat 1 5` | `si`·`so` 5초 내내 0, CPU 쉼 100% → **지금 메모리 압박 없음**. 꽉 찬 스왑 2GB는 오래된 잔여 |
| `ollama ps` | `llama3:latest` 5.3GB, `bge-m3:latest` 1.2GB — 둘 다 **100% CPU, UNTIL Forever**(계속 상주) |

- 어림: 5.9GB − 임베딩 모델 최대 3.4GB − PostgreSQL·FastAPI 약 0.6GB ≈ **1.9GB 남음** → 숫자로는 기준(1GB) 안. Ollama 모델이 Forever로 고정돼 있어, 누가 새 모델을 부르지 않는 한 메모리가 갑자기 늘지 않는다.
- 남는 위험: **CPU 경합.** llama3가 답을 만드는 동안(CPU로 수 초~수십 초) 코어를 다 써서 우리 질문 임베딩도 느려진다. 우리가 조절할 수 없다.
- 이 Ollama 모델(llama3·bge-m3)은 **기업 서버에 원래 있던 것으로, 우리 팀 것이 아니다**(11/07 최재영 확인). 우리는 쓰지 않고, 임베딩은 직접 만든 KURE-v1 인덱스로 간다.
- 기업 서버 메모리가 모자라면 **ARM 서버로 옮긴다**(여유 약 21GB — 메모리는 충분). 옮기기 전에 ARM에서도 1단계를 재서 속도를 확인하고, 앱·백엔드에서 닿는지(포트·방화벽), 서버가 시연 때까지 유지되는지(클라우드 무료 VM이면 오래 쉬면 회수될 수 있음)를 확인한다.
- 우리 PostgreSQL은 5432가 비어 있는지 확인하고, 아니면 다른 포트로(5433은 `drone-db`가 씀).

- **판단: 결정대로 기업 서버를 메인, ARM은 예비.** 최종은 2단계(백엔드와 같이)에서 확정한다.

### 권장: ARM 서버를 대기로 같이 준비

같은 모델·같은 인덱스 판본이면 벡터를 그대로 옮겨 쓸 수 있다. 기업 서버를 메인으로 두더라도 **ARM 서버에 같은 인덱스(`rag_chunk.csv` → `app.jobs.load_rag_index --apply`)를 미리 넣고 임베딩 모델을 받아 두면**, 시연 중 기업 서버가 흔들릴 때 API 주소만 바꿔 넘어갈 수 있다(ARM: 여유 약 21GB, 우리만 씀).

## 1단계 — 임베딩 혼자 (최소 조건)

두 서버 모두 같은 명령(이름표·결과 파일만 다르게). 서버 Python이 3.10이어도 **uv가 Python 3.12를 따로 받아** 쓰므로(서버의 기존 Python은 건드리지 않음) Docker가 필요 없다.

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
source $HOME/.local/bin/env            # 방금 설치한 uv를 이 터미널에서 찾게
git clone -b feature/rag-index-pipeline https://github.com/silversky621/AgeTech.git && cd AgeTech
uv sync --extra embed && uv run python -m agetech_data.rag.bench --label company-solo --json-out bench_company.json
#                                         ARM 서버는 --label arm-solo --json-out bench_arm.json
```

- 처음 한 번은 모델 2.3GB·torch 약 200MB·Python 3.12를 받느라 몇 분 걸린다. 측정은 1~2분(끝의 문서 임베딩 약 40초 동안 CPU를 꽉 씀).
- 다시 돌릴 때는 `git pull` 후 마지막 줄만, 앞에 `HF_HUB_OFFLINE=1 `을 붙인다(모델을 다시 확인하러 인터넷에 나가지 않게).
- 결과가 `move`이면 **여기서 끝 — ARM 서버로 옮긴다.** 혼자서도 안 되면 백엔드와 같이는 당연히 안 된다.
- `stay`여도 아직 합격이 아니다 → 2단계.
- Docker로 하고 싶으면 `rag_index_contract.md` 6절의 `docker run … python:3.12-slim` 명령도 같은 결과를 낸다.

## 2단계 — 백엔드와 같이 (실제 판정)

**주의: 모델이 두 번 올라가지 않게 한다.** 백엔드가 이미 KURE를 올린 상태에서 `bench`를 돌리면 모델이 두 개(약 6GB)라 실제보다 나쁘게 나온다. 둘 중 하나로 잰다.

### 2-A. 백엔드는 임베딩 없이, `bench`가 모델 역할 (백엔드에 RAG를 붙이기 전)

1. 이진녕: PostgreSQL + FastAPI를 시연과 같은 설정(워커 수, 다른 기능 포함)으로 띄운다. 임베딩 모델은 아직 올리지 않는다.
2. 최재영: 같은 서버에서

   ```bash
   uv run python -m agetech_data.rag.bench --label with-backend --concurrency 4 --threads 4 --passages 0 \
     --json-out bench_with_backend.json
   ```

   - `--concurrency 4`: 질문 4개가 동시에 들어오는 상황(시연 중 여러 명이 같이 누를 때)
   - `--threads 4`: torch가 코어를 다 잡지 않게 절반만 — 백엔드 요청이 같이 느려지지 않게
   - `--passages 0`: 문서 임베딩(전체 CPU를 수십 초 잡음)은 빼고 질문 임베딩만
3. 측정하는 동안 앱이나 `curl`로 백엔드 API를 몇 번 불러, 눈에 띄게 느려지지 않는지 본다.

### 2-B. 임베딩이 붙은 AI 도우미 API를 바깥에서 동시에 호출 (백엔드에 RAG를 붙인 뒤)

- 서버의 임베딩 모델은 프로세스 하나에만 올린다(FastAPI 워커 1개, 또는 작은 임베딩 서비스 하나).
- 질문 → 임베딩 → pgvector 검색 → (대화 AI 호출 전까지) 시간을 API 로그나 응답 헤더로 남기고, 동시에 4개씩 40번 정도 불러 p95를 본다.
- 대화 AI(외부 API) 응답 시간은 서버 사양과 무관하므로 따로 적는다.

## 판정 기준

| 항목 | 기준 | 넘으면 |
|---|---|---|
| 질문 임베딩 p95 (혼자) | ≤ 0.5초 | 옮김 |
| 질문 임베딩 p95 (동시 4개) | ≤ 1.0초 | 옮김 |
| 서버 전체 남은 메모리 (모델·백엔드 다 올린 뒤) | ≥ 1GB | 옮김 |
| 측정 중 스왑 증가 | ≤ 100MB | 옮김 |
| 백엔드 API | 측정 중에도 체감상 느려지지 않음 | 스레드를 줄여 다시 재고, 그래도 느리면 옮김 |

`bench`는 위 앞의 네 개를 자동으로 판정한다(종료 코드 0 = 유지, 2 = 옮김).

## 시연 운영 규칙 (어느 서버든)

1. **인덱스는 미리 만들어 넣는다.** 처음 전체 임베딩(약 25분, CPU 전부)은 서버에서 하지 않는다. `rag.export`의 CSV·`manifest.json`을 옮겨 서버 백엔드에서 `app.jobs.load_rag_index --apply`로 넣는다(11/14부터 psql 필요 없음).
2. **매일 갱신은 밤에**(예: 03:00). 시연 시간대에는 갱신을 멈춘다. 갱신이 실패해도 이전 판본이 그대로 검색된다.
3. 모델은 **프로세스 하나에만**, torch 스레드는 **코어의 절반**, `HF_HUB_OFFLINE=1`.
4. 시연 전날 `app.jobs.load_rag_index --verify`로 활성 판본·검색되는 청크 수를 확인한다. 직전 판본 하나는 적재 작업이 남겨 둔다(`--rollback <판본>`으로 되돌리기).
